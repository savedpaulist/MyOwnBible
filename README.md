# MyOwnBible (MOB / BibleOWN)

MyOwnBible — настольное приложение для углублённого изучения Библии на Rust и
GPUI. Оно объединяет чтение переводов MyBible, словари Strong's, морфологию,
комментарии, полнотекстовый поиск, Markdown-заметки, теги и тематические
цепочки в одном рабочем пространстве.

Приложение находится в бета-версии. Формат пользовательских данных уже
ориентирован на обычные Markdown-файлы и SQLite, но перед обновлением всё равно
рекомендуется делать экспорт в «Настройки → Синхронизация».

## Возможности

- несколько вкладок Библии и переход по ссылкам между местами Писания;
- переводы, словари, комментарии и перекрёстные ссылки формата MyBible;
- Strong's-номера H/G и морфологические данные для отдельных слов;
- полнотекстовый поиск с группировкой результатов по источникам;
- заметки Markdown, wiki-links и обратные ссылки;
- пользовательские комментарии к стихам, цветовые пометки и теги;
- тематические цепочки и вопросы для самостоятельного исследования;
- русский и английский интерфейс;
- синхронизация пользовательских данных через Google Drive `appDataFolder`;
- отдельное окно настроек и сохраняемая раскладка рабочих панелей.

## Быстрый старт

1. При первом запуске пройдите окно первоначальной настройки: выберите язык,
   тему, масштаб и папки приложения.
2. В «Общие → Папки приложения» укажите папку с модулями MyBible.
3. При необходимости укажите отдельную папку для Markdown-заметок. Её можно
   одновременно открыть в Obsidian или другом редакторе.
4. Выберите перевод в верхней части вкладки чтения. Нажатие на слово открывает
   сведения Strong's и морфологии, а правая кнопка мыши — действия со стихом.
5. Кнопка «Поиск» внизу показывает или полностью скрывает поисковую панель.
   Результаты раскрываются сначала по типу источника, затем по модулю.

Положение панелей, их размеры, открытые вкладки и последнее место чтения
сохраняются автоматически.

## Где взять модули

BibleOWN читает базы модулей MyBible (`*.SQLite3`). Подборка модулей доступна
на [ph4.ru](https://www.ph4.ru/b4_1.php).

Скачанные файлы обычно находятся внутри архивов. Распакуйте нужные переводы,
словари и комментарии из всех архивов в **одну общую папку**, затем выберите
эту папку в «Настройки → Общие → Папки приложения». После добавления или замены
файлов нажмите «Реиндексировать модули» в настройках.

## Заметки и пользовательские данные

Заметки являются обычными файлами Markdown. Ссылки вида `[[Название]]`
индексируются приложением, поэтому доступен список входящих и исходящих ссылок.
Теги, цепочки, вопросы, комментарии к стихам и визуальные пометки хранятся в
локальной базе состояния. Экспорт объединяет эти данные с копиями Markdown-
заметок в переносимую папку.

## Сборка для разработки

Понадобится актуальный Rust toolchain. Из корня проекта:

```sh
cargo build
cargo run
cargo test --workspace --all-targets
```

Обычная разработка не требует release-сборки. На Windows консоль скрывается
только у release-бинарника; debug-сборка оставляет её для диагностики.

## Сборки приложения и логотип

Изумрудный логотип хранится в `resources/branding` и подключён к сборкам:

- обычный `cargo build` на Windows встраивает `windows/mob.ico` в `.exe` как
  ресурс с ID `1`; этот же ресурс GPUI использует для окна и панели задач;
- для macOS `scripts/build-macos.sh --bundle` создаёт `.app` с `macos/mob.icns`;
- `mob-logo-master-1024.png` остаётся мастер-файлом для магазинов и будущих
  форматов упаковки.

### Release для Windows

Собирать Windows-версию лучше непосредственно на Windows. Откройте PowerShell,
перейдите в корень проекта и выполните:

```powershell
rustup update stable
cargo build --release
```

Готовое приложение появится здесь:

```text
target\release\bibleown.exe
```

Это уже графическая release-сборка для распространения:

- при запуске рядом с приложением не открывается окно командной строки;
- `resources/branding/windows/mob.ico` встроен непосредственно в `.exe`;
- иконка используется Проводником, окном приложения и панелью задач.

Для проверки запускайте именно `target\release\bibleown.exe`. Команда
`cargo run` без `--release` запускает debug-версию и намеренно оставляет
консоль для диагностических сообщений. Запуск release через Cargo выглядит
так:

```powershell
cargo run --release
```

### Release для macOS

Минимальная поддерживаемая версия — **macOS 10.15 Catalina**. Проект содержит
собственный упаковщик `.app`, поэтому установка `cargo-bundle` не требуется.
Сценарий проверяет версию macOS и выставляет deployment target 10.15.

```sh
sh scripts/build-macos.sh
sh scripts/build-macos.sh --release
sh scripts/build-macos.sh --bundle --release
```

Последняя команда создаёт обычное приложение
`target/release/bundle/osx/BibleOWN.app`. Его нужно открывать через Finder —
окно Terminal при этом не появляется.

Чтобы на Mac с процессором M1/M2/M3/M4 собрать приложение для старого Intel
Mac с Catalina, используйте отдельный режим:

```sh
sh scripts/build-macos.sh --bundle --intel-catalina --release
```

Он установит Rust-цель `x86_64-apple-darwin`, соберёт именно Intel-бинарник и
создаст пакет в
`target/x86_64-apple-darwin/release/bundle/osx/BibleOWN.app`. Обычная сборка,
созданная на M1 без `--intel-catalina`, является ARM64-приложением и на Intel
Mac не запустится независимо от указанной минимальной версии macOS.
Рядом автоматически создаётся ZIP-архив; для переноса на другой Mac лучше
использовать именно его, чтобы сохранить структуру пакета и права файлов.

Бэкенд GPUI в проекте использует совместимый с Catalina API типов файлов и не
линкует отсутствующий там `UniformTypeIdentifiers.framework`.

Готовый пакет находится в `target/release/bundle/osx/BibleOWN.app`. Именно
пакет `.app` получает `resources/branding/macos/mob.icns` и отображает иконку
в Finder и Dock. Обычный `cargo build --release` также собирает исполняемый
файл, но не создаёт полноценный macOS-пакет приложения.

Проверить готовый пакет на Mac можно так:

```sh
/usr/libexec/PlistBuddy -c 'Print :LSMinimumSystemVersion' \
  target/release/bundle/osx/BibleOWN.app/Contents/Info.plist
otool -l target/release/bundle/osx/BibleOWN.app/Contents/MacOS/bibleown \
  | grep -A5 LC_BUILD_VERSION
```

В обоих случаях минимальная версия должна быть `10.15`.

Для бета-теста на Catalina рекомендуется отдельный Intel-пакет, а не
универсальный bundle: так проще проверить реальную архитектуру и минимальную
версию каждого исполняемого файла.

## Синхронизация и перенос данных

В разделе «Настройки → Синхронизация» можно подключить свой Google Drive. BibleOWN
отправляет изменения напрямую в служебную папку приложения на диске пользователя.
Модули, индексы, настройки интерфейса и открытые вкладки хранятся на устройстве.
Проекты Google Cloud и аккаунты образуют отдельные хранилища. Для обмена на двух
устройствах используйте один проект OAuth и один аккаунт Google.

### Подготовка сборки с входом через Google

1. В [Google Cloud Console](https://console.cloud.google.com/apis/library/drive.googleapis.com)
   создайте проект и включите Google Drive API.
2. В **Google Auth Platform** настройте **Branding** и **Audience**. Для пробного
   подключения в режиме **Testing** добавьте свой Google-аккаунт в тестовые
   пользователи.
3. В **Clients** создайте один OAuth-клиент типа **Desktop app** для всех
   устанавливаемых копий приложения. Скопируйте Client ID. Client secret для
   desktop-приложения не является конфиденциальным и в этой реализации
   необязателен благодаря PKCE. [Инструкция Google](https://developers.google.com/identity/protocols/oauth2/native-app)
4. Передайте Client ID как переменную окружения при сборке. Он будет встроен в
   бинарник, поэтому пользователю на новом устройстве не потребуется JSON-файл.
   Пример для macOS и Linux:

   ```sh
   BIBLEOWN_GOOGLE_CLIENT_ID='ваш-client-id.apps.googleusercontent.com' cargo build --release
   ```

   PowerShell:

   ```powershell
   $env:BIBLEOWN_GOOGLE_CLIENT_ID = 'ваш-client-id.apps.googleusercontent.com'
   cargo build --release
   ```

   Если конкретный OAuth-клиент требует Client secret, его по-прежнему можно
   передать через `BIBLEOWN_GOOGLE_CLIENT_SECRET`, но считать его секретом внутри
   распространяемого desktop-бинарника нельзя.

Для закрытого теста оставьте Audience в режиме **Testing** и добавьте тестовые
аккаунты. Учтите, что выданные в этом режиме разрешения, включая refresh token,
истекают через 7 дней. Для длительного бета-теста переведите External-приложение
в **In production**, заполните Branding, домашнюю страницу и политику
конфиденциальности. Используемый scope `drive.appdata` относится к
non-sensitive и даёт доступ только к скрытой папке данных этого приложения.

### Подключение в BibleOWN

В готовой сборке откройте «Настройки → Синхронизация» и нажмите
**«Подключить Google Drive»**. Выберите аккаунт в браузере, разрешите доступ и
вернитесь в BibleOWN. Статус сменится на **«Google Drive подключён»**, после
чего начнётся обмен данными. Для сборок без включённого клиента доступна кнопка
«OAuth-клиент…», которая принимает JSON для локальной разработки.

На Linux для Drive нужны
`curl`, `secret-tool` и работающая служба Secret Service. На Windows используется
системный `curl.exe` и диспетчер учётных данных, на macOS — системный `curl` и связка ключей.

**Экспортировать…** создаёт папку с `bibleown.json` и обычными Markdown-файлами
в подкаталоге `notes`. В JSON входят цепочки, вопросы, теги, пометки, личные комментарии,
параллельные места и, если имеются, версии записей из конфликтов. Экспорт хранится
в открытом виде. Markdown можно сразу открыть в другом редакторе. **Импортировать…**
принимает эту папку в BibleOWN и сохраняет разные версии совпадающих записей для
выбора. Экспорт и импорт работают через локальные файлы.
